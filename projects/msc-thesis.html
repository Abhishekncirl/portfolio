Real-Time Inventory Optimization on AWS

In plain English

What the project does

Imagine a shop that watches every sale as it happens. The moment stock runs low or piles up, the system tells the owner and suggests what to reorder, before any human has to check a spreadsheet.

This thesis builds exactly that, but on the cloud. Live sales data flows into AWS, a small piece of code checks it, a trained machine-learning model forecasts the next week of demand, and alerts go out instantly if anything is about to go wrong. No servers to run, no reports to refresh, and the whole thing costs about €62 a month.

The problem

Traditional inventory systems run on nightly batches and spreadsheets. By the time a report shows a stockout, the customer has already left. Multi-location supply chains and seasonal demand only make this worse.

Reactive, not real-time

Decisions are made against yesterday's data, so sudden demand spikes and dips go unseen until after the fact.

Over- and under-stock cost

Carrying too much stock ties up cash. Not enough stock loses the sale and the customer.

Manual, error-prone work

Analysts spend hours reconciling CSVs. The real question (what should I order tomorrow?) gets pushed to the end of the day.

Scaling is painful

On-prem systems don't scale with demand peaks. Provisioning extra capacity in advance wastes budget.

Research question

The question

How can real-time inventory optimization using AWS Lambda, SageMaker and Kinesis predict the efficiency and accuracy of inventory management in retail supply chains?

Architecture at a glance

Eight AWS services, one data path. Raw stock events stream into Kinesis, Lambda validates and routes them, SageMaker forecasts, DynamoDB stores the live state, SNS alerts the team, CloudWatch watches everything, and QuickSight paints the picture.

Methodology

Six steps, in order. As you scroll, each one turns green when the camera reaches it.

  1. 1

    Collect & clean

    Historical inventory data pulled from Kaggle. Duplicates, nulls and obvious outliers removed; the clean dataset lands in an S3 bucket.

  2. 2

    Train the model

    80/20 split in SageMaker. The model learns stock-level patterns over time so it can flag over- and under-stock before they happen.

  3. 3

    Deploy the endpoint

    Trained model published as a SageMaker endpoint. Lambda calls it on every real event, so predictions are always based on live traffic.

  4. 4

    Stream live events

    Every sale, return and transfer is pushed into Kinesis Data Streams. Lambda picks each one up in milliseconds and validates it.

  5. 5

    Decide + act

    Lambda compares live stock against safe bounds. Over the limit? SNS fires an overstock alert. Under it? An understock alert. Clean data lands in DynamoDB for the dashboard.

  6. 6

    Watch + learn

    CloudWatch captures every log and latency. QuickSight gives humans a readable view. Fresh patterns feed back into SageMaker, retraining the model so it keeps getting better.

What it means

  • It works end to end. Real stock events → live decision → stored state → human-readable dashboard, in under five minutes per round-trip.
  • It pays for itself. Six services for about €62/month, with SageMaker the only serious line item. Everything else sat inside the AWS free tier.
  • The model learns. A feedback loop writes fresh patterns back into SageMaker so the forecast stays current instead of decaying.
  • It scales without touching servers. Lambda and Kinesis absorb traffic spikes without pre-provisioning capacity.

Honest limits + next steps

Dataset breadth

Trained on a single Kaggle dataset. Testing across more industries would prove generality.

Reactive, not predictive cost

Cost is tuned after the fact. Future work: predictive cost analytics that pre-size SageMaker for upcoming demand.

Finer cost breakdown

Break Kinesis shard-hours and SageMaker instance-hours down line-by-line for sharper optimisation.

Automated right-sizing

Use AI-driven cloud management to resize SageMaker endpoints when forecast demand changes.
